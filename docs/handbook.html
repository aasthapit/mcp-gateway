Overview

One MCP endpoint, a different tool set for every caller

The gateway sits in front of any number of upstream MCP servers and presents them as a single streamable-HTTP endpoint. Each request is answered with exactly the tools the caller is allowed to see: a guest set for anonymous clients, more for clients that present a valid JWT. The allow-lists live in MongoDB, are edited through an admin UI, and reach every running replica within about half a second without a restart.

It exists for one reason: an organisation wants to expose internal MCP servers to many clients (IDE agents, CI bots, partner integrations) through one address, and control per client which tools are reachable, with that control changeable at runtime by people who are not the gateway's operators.

What a client sees when it calls tools/list:

  • No token: the tools in every toolset granted to anonymous. In the shipped seed that is sample-public_time_now and sample-public_echo.
  • A valid bearer token: the guest set plus every toolset whose grant matches the token's claims (a realm role, a group, a scope, a client id). A developer with the mcp-developer role also gets sample-private_secret_lookup.
  • A bad token: HTTP 401 with an RFC 9728 challenge. A broken token is never downgraded to guest.

Calling a tool that is not on the caller's list answers exactly like calling a tool that does not exist, so the existence of hidden tools is not revealed.

How it works

Request path

Every MCP request crosses two of our own layers before FastMCP forwards it upstream. The first decides who is calling; the second decides what they may see. Neither keeps per-connection state, so any replica can answer any request.

→

→

Three details matter in that picture:

  • The auth layer wraps only /mcp. Health, metrics, the RFC 9728 metadata document and the token-guarded /internal/* routes are plain Starlette routes outside it.
  • List filtering alone would not be enough: a client can call a tool it never listed. The middleware checks both, and a denied call raises the same "unknown tool" error FastMCP itself produces.
  • Dev-only gateway tools such as gateway_whoami bypass the allow-list; the policy governs proxied upstream tools only.

Policy model

The policy is four collections in the mcp_gateway database. The JSON Schemas under schemas/ are the single source of truth: a script turns them into Mongo $jsonSchema validators, the admin API validates request bodies with them through ajv, and the gateway's pydantic models mirror them.

upstreams

One document per proxied server. The _id becomes the tool namespace, so upstream tool echo on sample-public is sample-public_echo.

{
  "_id": "github",
  "displayName": "GitHub MCP",
  "enabled": true,
  "transport": "http",
  "url": "http://mcp-github.mcp-upstreams.svc:8080/mcp",
  "auth": { "type": "static_bearer", "secretRef": "upstream-github" },
  "sessionMode": "shared",
  "protocolMode": "2026-07-28",
  "timeoutsMs": { "connect": 2000, "call": 60000 },
  "cacheTtlSec": 300
}

toolsets

Named allow-lists. Entries are namespaced tool names or fnmatch globs. An explicit deny wins over every allow in the caller's union.

{
  "_id": "public-basics",
  "enabled": true,
  "allow": ["sample-public_time_now", "sample-public_echo"],
  "deny": []
}
{
  "_id": "engineering",
  "enabled": true,
  "allow": ["sample-private_*"],
  "deny": []
}

grants

Who gets which toolsets. Subject kinds: anonymous (matches everyone, the guest floor), authenticated (any valid token), claim (a dotted path into the claims with eq, in, contains or exists), client_id.

{
  "_id": "developers",
  "enabled": true,
  "subject": {
    "kind": "claim",
    "path": "realm_access.roles",
    "op": "contains",
    "value": "mcp-developer"
  },
  "toolsets": ["public-basics", "engineering"]
}

meta and policy_history

meta holds one document, {_id: "policy", version}. Every admin write bumps the version in the same transaction, so pods can confirm freshness with one cheap read. policy_history is append-only: collection, id, actor, time, before and after.

{ "_id": "policy", "version": 268,
  "updatedAt": "2026-10-15T23:12:04Z",
  "updatedBy": "admin1" }

Evaluation rule. Effective tools = the union of allow across the enabled toolsets of every enabled grant that matches the principal, minus the union of their deny. Nothing is allowed by default. Anonymous grants apply to everyone, so an authenticated user always sees at least the guest set. The result is memoised per principal key (kind plus the sorted ids of the matching grants), so a busy pod computes it once per distinct caller shape.

Secrets never enter Mongo. An upstream's auth.secretRef names a file under GATEWAY_UPSTREAM_SECRETS_DIR, which is a mounted Kubernetes Secret in the cluster and an environment variable fallback on a laptop.

Hot reload

Each gateway process runs one PolicyWatcher. It has two ways of learning about a change and one way of applying it.

  1. Initial load. On startup the watcher reads all four collections with readConcern: majority, builds an immutable snapshot and swaps it in. /readyz stays 503 until that first load succeeds. If Mongo is down the pod keeps retrying and serves nothing meanwhile.
  2. Change stream. One database-level change stream per process, filtered to the four collections. Any event is debounced for 250 ms into a single full reload. The resume token is kept in memory; a resumable error reopens from it, and a lost history or an invalidate falls back to a full reload.
  3. Version poll. Every 30 s the watcher reads meta.version and reloads if it moved. This covers a dead stream and Mongo tiers that cap change streams; correctness never depends on the stream, only latency does.
  4. Apply. After a swap the watcher reconciles the upstream registry (mount new, unmount disabled, re-mount changed) and publishes notifications/tools/list_changed on an in-process subscription bus. Modern clients with an open subscriptions/listen stream are told at once; everyone else re-lists when the 30 s ttlMs hint on their last list expires.

A failed reload keeps the previous snapshot in service and the pod stays ready. gateway_policy_staleness_seconds measures the time since the store last confirmed the snapshot and drives the stale-policy alert. Measured on the local stack, an edit shows up in the next tools/list after about 0.34 s, and a forced replica-set step-down is absorbed by the driver's own resume.

Protocol and statelessness

The current MCP specification revision, 2026-07-28, removed protocol-level sessions and the Mcp-Session-Id header. Every request carries its protocol version and client capabilities in _meta, and the specification allows the tool list to vary by the authorization presented on the request. That is exactly the gateway's model, so modern clients need nothing special from the infrastructure.

Older clients still open with an initialize handshake. The gateway serves them with stateless_http=True: it never mints a session id and refuses the legacy GET stream. Those clients lose push notifications and simply re-list on their own schedule. The consequence for operations is pleasant: no sticky sessions, no shared session store, and horizontal scaling by adding pods.

Server push for modern clients uses the SDK's subscriptions/listen: a long-lived POST whose response is an SSE stream. FastMCP writes a : ping comment every 15 s on every open stream, so the OpenShift router's 30 s idle timeout never fires on them; the Route's 1 h timeout annotation is there for slow tool calls.

Security model

RequestResult
No Authorization headerAnonymous principal. With GATEWAY_ALLOW_ANONYMOUS=false the gateway is strict and answers 401 instead.
Bearer JWT that verifiesUser principal with sub, client_id, scopes and claims. Verified against the issuer's JWKS, with iss, aud, exp and nbf checked and an explicit asymmetric algorithm allow-list.
Bad signature, expired, wrong issuer or audience, unknown key id after a throttled JWKS refresh, disallowed algorithm, malformed, non-Bearer scheme401 {"error":"invalid_token"} plus WWW-Authenticate: Bearer resource_metadata="…/.well-known/oauth-protected-resource", error="invalid_token"
Token in the query string or a cookieIgnored, treated as absent. The specification forbids tokens in URLs.
  • Client tokens stop at the edge. FastMCP proxies forward inbound headers upstream by default; the gateway turns that off and authenticates to each upstream with its own credential from a Secret. The specification says a resource server must not pass client tokens through.
  • JWKS caching. Keys are cached per key id for an hour and refreshed on an unknown id no more than every five minutes. During an IdP outage known keys keep verifying, the fetch is bounded at 3 s, and refreshes happen in the background.
  • Host and origin. FastMCP's DNS-rebinding guard is on; extra hosts are listed in GATEWAY_ALLOWED_HOSTS.
  • Container hygiene. UBI 9 minimal images, numeric non-root user, group-0 writable app dir, read-only root filesystem with an emptyDir on /tmp, all capabilities dropped, ports 8080 and 9090 only. The conftest policy in deploy/policy fails the build if a rendered Deployment breaks any of that.
  • Prod guards. With GATEWAY_ENV=prod the settings refuse stdio upstreams, a non-https public base URL or issuer, a static policy source and console logs.

Admin API and UI

Operators and policy owners never touch Mongo directly. The admin API is the only writer, and it follows one rule for every mutation: validate the body against the shared schema, then in one transaction with writeConcern: majority write the document, increment meta.version and append a policy_history entry. A PUT with unchanged content is a no-op. Deleting a toolset a grant still references, or an upstream a toolset pattern still names, answers 409 with the referencing ids.

Admin calls need a bearer token with aud=mcp-admin and the realm role mcp-admin. In the shipped Keycloak realm only admins receive that audience: the mcp-admin resource client's role is a composite of the realm role, so a developer's token is accepted by the gateway and rejected by the admin API.

EndpointWhat
GET /api/{upstreams|toolsets|grants}{items, version}
PUT /api/{collection}/:idCreate or replace; 400 with details: [{path, message}] on schema errors; returns the new version
DELETE /api/{collection}/:id409 with referencedBy when something still points at it
GET /api/history?collection=&id=&limit=Newest first, with before and after
GET /api/catalogEvery tool across mounted upstreams, proxied from the gateway's /internal/catalog; feeds the UI's tool picker
POST /api/preview{kind:"anonymous"}, {claims:{…}} or {token:"…"} (decoded without verification, labelled as such) → tools and matching grants for that principal
GET /api/upstreams/health, POST /api/upstreams/reloadProxied from the gateway's internal routes

The UI has five pages: Upstreams (schema-driven form, live health badges, a reload button, secretRef as a name never a value), Toolsets (allow and deny editors with a catalog picker and a live "matches N catalog tools" hint for each glob), Grants (subject builder and toolset multi-select), Preview (effective tools for a guest, a claims JSON or a pasted token) and History (table with a before/after diff). Every save shows the resulting meta.version.

The gateway's /internal/* routes require the X-Internal-Token header, compared in constant time to GATEWAY_INTERNAL_TOKEN, and in the cluster a NetworkPolicy limits them to the admin-api pod. The admin chart reads that token from the gateway's own Secret so the two sides can never disagree.

Observability and limits

Metrics

Prometheus text on /metrics and on the separate :9090 listener. The names you will build dashboards on:

  • gateway_requests_total{method,era,principal_kind,outcome} and gateway_request_duration_seconds
  • gateway_tool_calls_total{tool,upstream,principal_kind,outcome} and gateway_tool_call_duration_seconds
  • gateway_policy_denials_total{tool,principal_kind}, gateway_policy_version, gateway_policy_staleness_seconds, gateway_change_stream_up
  • gateway_upstream_up{upstream}, gateway_upstream_probe_seconds, gateway_upstream_errors_total{upstream,kind}, gateway_upstreams_mounted
  • gateway_http_responses_total{route,code}, gateway_rate_limited_total, gateway_response_truncated_total, gateway_open_listen_streams
  • gateway_auth_results_total{result}

Tracing and audit

GATEWAY_TELEMETRY_MODE=native installs the OpenTelemetry SDK with an OTLP exporter (http/protobuf or grpc). FastMCP emits one server span per MCP request, delegate spans into the mounted proxies and client spans to upstreams, with context carried in _meta. The gateway adds the principal kind, client id, policy version and upstream as span attributes, continues an incoming traceparent, and stamps trace_id on every log line written inside a span. The default is off.

Logs are JSON lines. Every tools/call and every denial produces one audit line with principal kind, sub, client id, tool, upstream and outcome; every auth rejection carries a reason code.

Limits, all per pod

  • Rate limit: token buckets keyed user:<sub> for users and ip:<client ip> for guests, 50 and 20 requests per second by default. The client IP comes from X-Forwarded-For only when the peer is in GATEWAY_TRUSTED_PROXIES; the chart trusts the router network. A rejected request gets JSON-RPC error -32000.
  • Response size: results above GATEWAY_RESPONSE_MAX_BYTES (1 MB) become one truncated text block. While this is on, listed tools lose outputSchema, because a truncated result cannot match it; set the limit to 0 to keep the schemas.
  • Body size: requests above 1 MiB get 413 before they reach MCP.
  • Graceful shutdown: on SIGTERM the pod turns /readyz to 503, closes listen streams with their final result so clients re-listen elsewhere, then gives in-flight calls up to 45 s. A unit test proves the sequence; the rolling-restart drill shows zero 5xx behind a balancer.

N replicas admit N times the configured rate. Cluster-wide limits would need a shared store and are deliberately left for a later version.

Setup

Local stack

Everything runs on one machine: Mongo as a single-node replica set (change streams and transactions need one), Keycloak with a dev realm, the two sample upstreams and an OTel collector. The gateway and the admin services run on the host for hot reload.

Prerequisites: Podman (or Docker), Python 3.12 or newer, uv, Node 22 or newer. On macOS:

brew install podman docker-compose uv
podman machine init && podman machine start

Then from the repository root:

make seed        # load local/seed/*.json and bump meta.version

Connect a client

Any MCP client that speaks streamable HTTP works. With the FastMCP Python client, a string auth= becomes the bearer header:

from fastmcp import Client

async with Client("http://localhost:8080/mcp") as c:                  # guest
    print([t.name for t in await c.list_tools()])  # sample-public_time_now, sample-public_echo
    print((await c.call_tool("sample-public_echo", {"text": "hi"})).data)

async with Client("http://localhost:8080/mcp", auth=token) as c:      # dev1
    print([t.name for t in await c.list_tools()])  # + sample-private_secret_lookup
    print((await c.call_tool("gateway_whoami", {})).data)             # dev only: the resolved principal

Raw HTTP for the modern protocol era needs the _meta envelope plus the mirrored headers; this is what the smoke and load tests send:

curl -s -X POST http://localhost:8080/mcp \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: 2026-07-28" -H "Mcp-Method: tools/list" \
  -H "Authorization: Bearer $(make -s token)" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{"_meta":{
        "io.modelcontextprotocol/protocolVersion":"2026-07-28",
        "io.modelcontextprotocol/clientCapabilities":{}}}}'

A client that only learns about authentication from a 401 will not discover that elevated tools exist, because guests get 200. The RFC 9728 metadata document is published regardless, and GATEWAY_ALLOW_ANONYMOUS=false turns on the strict behaviour for deployments that want the challenge.

Write policy

Through the UI: sign in as admin1 at http://localhost:3000, open Grants, tick a toolset, save, and watch the version number change. Through the API, the same thing with curl:

# admin1 token carries aud=mcp-admin and the mcp-admin role
TOKEN=$(make -s token-admin)

# a new toolset
curl -s -X PUT localhost:3001/api/toolsets/reporting \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"enabled":true,"allow":["sample-public_time_now"],"deny":[]}'

# grant it to every authenticated caller
curl -s -X PUT localhost:3001/api/grants/all-users \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"enabled":true,"priority":80,"subject":{"kind":"authenticated"},"toolsets":["reporting"]}'

# what would a CI client see?
curl -s -X POST localhost:3001/api/preview \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"claims":{"azp":"ci-runner"}}'

Claim paths follow your identity provider: Keycloak realm roles live at realm_access.roles, Entra app roles at roles with scopes in scp, Okta groups at groups. The contains operator also understands space-separated string claims such as scope.

Rolling back is a matter of reading the previous document from policy_history and putting it back; the runbook has the exact steps.

Add an upstream

Upstreams are documents in the upstreams collection; the gateway mounts a new one live on the next reload and unmounts a disabled one just as quickly.

  1. Make it reachable over HTTP. In the cluster, upstreams are Deployments in the mcp-upstreams namespace, which the gateway's NetworkPolicy already allows. A stdio-only server gets a small HTTP shim; stdio from inside the gateway pod is refused in production.
  2. Provide its credential. Add a key to the gateway's upstream-secrets Secret (ESO in prod); the file name is what secretRef refers to. Locally, set GATEWAY_UPSTREAM_SECRET_<REF>.
  3. Create the document through the admin API or UI. Pin protocolMode to 2026-07-28 for FastMCP 4 servers and use sessionMode: shared; auto-negotiation costs an extra round trip per connection and per-request sessions re-initialise on every call.
  4. Grant its tools. Nothing is visible until a toolset allows <id>_* or specific names and a grant hands that toolset to someone. The catalog picker in the UI lists the discovered tools as soon as the upstream is mounted.

A dead upstream stays mounted and marked down: its tools keep listing from cache, calls to it fail fast with a clear connect error, the other upstreams are unaffected, and readiness does not flip. A missing secret leaves the upstream degraded and unmounted with the reason visible on the health page.

Deploy to OpenShift

Two Helm charts, mcp-gateway and mcp-admin, plus manifests for the namespaces, a Percona MongoDB cluster, Argo CD applications and a Tekton pipeline. Cluster prerequisites: OpenShift 4.16 or newer, the Percona Operator for MongoDB, the External Secrets Operator (prod), OpenShift GitOps, OpenShift Pipelines for the build, and user workload monitoring for the ServiceMonitor. The charts have been validated by rendering and policy checks; applying them to a live cluster is the one step that has not yet been exercised.

HPA and PDBProd: 3 to 10 replicas on 60 % CPU, optional custom metric gateway_open_listen_streams; PDB minAvailable: 2. With the HPA on, the Deployment carries no replicas field so Argo CD and the HPA never fight
NetworkPolicyDefault deny both ways; ingress from the router namespace and the admin-api pod on 8080 and from monitoring on 9090; egress to DNS, the Percona pods, the mcp-upstreams namespace, non-RFC1918 443 for the IdP and the OTel collector
SecretsProd: ExternalSecrets from a ClusterSecretStore for the Mongo URI, the internal token, the upstream credentials (mounted as files) and the Percona users. Dev: plain Secrets from values; the chart refuses that combination when config.ENV=prod
ServiceMonitor and PrometheusRuleScrape every 30 s; six alerts, each unit-tested with promtool as part of make deploy-check

Production through GitOps

Production is never installed by hand. The Tekton pipeline tests, builds with buildah, scans with Trivy, promotes the image by digest with skopeo and commits the digest into values-prod.yaml on the release branch; Argo CD renders and syncs. Rollback is a git revert of that bump. The prod render fails on purpose if route.host is empty, because the gateway refuses a non-https public base URL in prod.

Before anything is applied, make deploy-check runs locally and in CI: helm lint --strict, a template render per overlay, kubeconform against the Kubernetes 1.32 schemas plus the Route, ExternalSecret, ServiceMonitor, PrometheusRule, Percona, Argo CD and Tekton CRDs, the conftest policy for the restricted SCC and workload hygiene, promtool rule tests, and kube-score as an advisory pass.

Alerts, each with a runbook entry

AlertFires when

McpGatewayHigh5xxRatioMore than 2 % of /mcp responses are 5xx over 5 minutes

The runbook (docs/runbook.md) walks each alert from symptom to checks to action, and also covers rolling back a policy change from policy_history, rotating the internal token, upstream credentials and Mongo credentials, and scaling. make drills rehearses the failure modes locally: a Mongo primary restart under traffic, an upstream going down and back, the identity provider refusing or unreachable, and a rolling restart of two processes behind a balancer.
